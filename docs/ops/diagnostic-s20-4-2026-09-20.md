# Diagnostic — S20.4, et la candidature sourcing qu'ORQA efface

**Date** : 20/09/2026 · **Base** : dev · **Statut** : DIAGNOSTIC, aucun correctif appliqué.
**Origine** : seul échec de la suite de régression, présent avant comme après la branche
`fix/validations-orphelines` — donc antérieur à elle.

```
S20.4 — une candidature en cours de création ARRÊTE l'effacement
  › rend un arrêt qui se lève seul, et l'exécution refuse de détruire la saisie
AssertionError: expected [] to deeply equal [ 'sourcing_admission_pending' ]
```

La réponse est en deux parties : **le test n'est pas en cause**, et **il avait raison de tomber**.

---

## 1. Pourquoi le test tombe : le serveur de dev mange la ligne

`npm run test:regression` **serveur de dev ÉTEINT** : **232 tests sur 232, zéro échec.**
Le même serveur rallumé : S20.4 tombe, de façon reproductible.

Le mécanisme, sondé :

| Sonde | Ce qu'elle a montré |
|---|---|
| Résolution du périmètre | correcte — `identity.sourcingApproachIds` contient bien l'approche |
| La ligne en base au moment de l'assertion | `status: "active"` · `submitted_at: null` · **`submission: null`** — alors que le semis pose `admission_pending` + une saisie |
| `updated_at` | **2 à 21 secondes après** `created_at`, donc pendant le run |
| Journal | `sourcing_admission_refused { approachId: …, campaignStatus: "active", scoringSheetValidated: false }` |
| Pile d'appel dans le process de test | **`releaseSubmission` n'y est jamais appelée** |

L'écriture vient donc d'un **autre process**. C'en est un seul : le serveur `next dev`, dont
`instrumentation.ts` démarre le planificateur IMAP, qui appelle `runSourcingMaintenance()`
toutes les 30 s **contre la même base dev**. La reprise des admissions balaie
`listPendingAdmissions(20)` — **sans aucun filtre de périmètre** : elle attrape la ligne que la
régression vient de semer.

> C'est le piège déjà consigné pour la régression sourcing (« le tick du scheduler garde le code
> du démarrage : redémarrer avant »), mais un cran plus loin : ici il ne s'agit pas de code
> périmé, c'est que **le rail de maintenance et la suite de régression travaillent sur la même
> base, et le rail n'a aucune raison de savoir qu'une ligne appartient à un test.**
>
> Conséquence pratique, à connaître : **`npm run test:regression` doit tourner serveur de dev
> arrêté**, sinon S20.4 (et potentiellement tout scénario sourcing en attente) est faussement
> rouge. À défaut, restreindre `listPendingAdmissions` aux campagnes hors préfixe de test.

---

## 2. Pourquoi il avait raison de tomber : la saisie du candidat est DÉTRUITE

Le test s'appelle « **l'exécution refuse de détruire la saisie** ». La saisie a bien été
détruite — pas par l'effacement RGPD, mais par le produit lui-même.

### 2.1 Le chemin

`admitSourcedCandidate` (`src/lib/sourcing/server/admit.ts:60-72`) :

```ts
const campaign = await getCampaign(approach.campaignId);
const sheet = campaign?.scoringSheet?.isValidated ? campaign.scoringSheet : null;
if (!campaign || campaign.status !== 'active' || !sheet || !(await canInviteForCampaign(campaign.id))) {
  await releaseSubmission(approach.id);      // ← irréversible
  await appendJournalEntry({ action: 'sourcing_admission_refused', … });
  return { kind: 'closed' };
}
```

`releaseSubmission` (`src/lib/db/repos/sourcing-admission.ts:133-140`) :

```ts
.update({ status: 'active', submitted_at: null, submission: null, … })
```

`submission` est un `StoredSubmission` : la saisie **et** le pointeur vers le CV téléversé
(`{ bucket, storagePath, fileName, mime }`). Le mettre à `null` perd les deux — le fichier reste
orphelin dans le stockage, plus rien ne le référence.

### 2.2 Quatre causes très différentes, une seule conséquence

| Cause du refus | Nature | Conséquence appliquée |
|---|---|---|
| La campagne n'existe plus | définitive | saisie détruite |
| La campagne n'est plus active | définitive (ou suspension) | saisie détruite |
| **La fiche de scoring n'est pas validée** | **transitoire** | saisie détruite |
| **Aucun agenda réservable (`canInviteForCampaign`)** | **transitoire** | saisie détruite |

Les deux dernières se résolvent en validant une grille ou en déclarant des disponibilités. Le
dossier attend dix minutes, et la candidature est perdue définitivement.

C'est exactement le cas observé : `campaignStatus: "active"`, `scoringSheetValidated: false`.

### 2.3 Le même produit fait l'inverse sur l'autre porte d'entrée

Doctrine du chemin email, écrite noir sur blanc (audit C4) :

> **« Fiche de scoring non validée ≠ CV perdu »** — le binaire est **stocké** et mis en file
> `imap_unmatched_cvs` `reason='pending_sheet'` ; la file est **drainée automatiquement** dès que
> la campagne est active et la fiche validée.

Une même personne, un même CV, une même campagne sans fiche validée :

| Arrivée | Résultat |
|---|---|
| Par **email** | conservé, mis en file, rejoué automatiquement |
| Par **sourcing** | **détruit** |

### 2.4 Et la personne ne le saura jamais

Après le reset, `resolveLandingState` (`src/lib/sourcing/landing.ts:29-33`) : l'approche est
`active`, la campagne est `active` ⇒ `{ kind: 'form' }`. Celui qui rouvre son lien retrouve
**le formulaire vierge**, comme s'il n'avait jamais rien envoyé. Aucun mail ne part. La seule
trace est `sourcing_admission_refused` au journal.

Or la route de soumission lui a répondu, elle : *« votre candidature est bien reçue, vous
recevrez un email pour choisir un créneau »* (S24 — soumission asynchrone). **Le produit promet,
puis efface.**

## 3. Ce que je propose

Aucun correctif appliqué : le geste juste est un arbitrage métier, et il en existe déjà un dans
le produit pour la situation identique.

| # | Correctif | Effort |
|---|---|---|
| **1** | **Séparer les causes définitives des causes transitoires.** `sheet` non validée et `canInvite` faux ⇒ **`deferred`**, pas `closed` : la ligne reste `admission_pending`, le rail la reprendra. C'est déjà le vocabulaire de `AdmissionOutcome`, et exactement ce que fait le chemin email avec `pending_sheet`. | **S** |
| **2** | **Ne jamais détruire la saisie sur un refus.** Même définitif (campagne clôturée), la conserver le temps d'en informer la personne, ou la classer — pas l'effacer en silence. Au minimum : ne pas perdre le pointeur du CV, qui laisse un fichier orphelin au stockage. | **S** |
| **3** | **Dire la vérité au candidat.** Si le refus est définitif, son lien doit afficher « cette offre est fermée », pas un formulaire vierge qui contredit le « bien reçue » qu'il a lu. | **S** |
| **4** | **Borner le rail au hors-test.** `listPendingAdmissions` exclut le préfixe de campagne de test, ou la régression exige un serveur de dev arrêté (documenté dans le runbook). | **XS** |

⚠️ **Le correctif 1 a une borne** : un différé sans fin est un autre silence. Le compteur
`admission_attempts` et `admissionRetryDue` existent déjà — il faut une **issue signalée** après
N tentatives (comme `imap_cv_analysis_abandoned`), pas une boucle.
