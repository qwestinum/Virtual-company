## Décisions structurantes (visées par le DO)

1. **Sans-suite = dimension orthogonale**, jamais un 3ᵉ statut ; taux des
   rapports sur les évaluées ; `retenu` non classable ; gris `sending`
   différé ; mails selon matrice par raison ; « Rouvrir » en V1.
   → `docs/specs/candidatures-sans-suite.md`
2. **Multi-user : espace commun, agendas/rôles individuels** ; Cal.com
   **option A** (comptes séparés, un webhook par compte, même secret — piège
   du webhook team documenté) ; rôle depuis `recruiters.role` seul ;
   `/api/metrics/global` scindé, pas gaté en bloc.
   → `docs/specs/multi-utilisateur.md` + `docs/ops/multi-utilisateur.md`
3. **Règle absolue `migrate.sql` = état final idempotent** : un bloc
   canonique par contrainte, guards sur la DÉFINITION, validation par DOUBLE
   application dev. Incident de référence 30/07 (CHECK 3 valeurs rejoué sur
   des rows `void`).
4. **Seed admin manuel par environnement** (ordre impératif : migration →
   seed → déploiement du gate) — un seed automatique cléé sur un email
   no-opait en silence.

## Incidents rencontrés et leçons

- **23514 au rejeu de `migrate.sql`** → règle « état final » (cf. ci-dessus).
- **`recruiters` vide après migration** → seed manuel + vérification
  bloquante avant déploiement.
- **`cookies()` hors scope de requête** : tout helper d'auth appelé par des
  handlers invocables in-process doit être fail-soft (null = pas de session).
- **Assertions de régression** : ne jamais figer un accord grammatical ni un
  état de base variable ; respecter les invariants du modèle dans les setups
  (cochées ⊆ connues).
