# Audit UX ORQA — normes, densité, parcours

**Date** : 20/09/2026 · **Périmètre** : parcours principal (créer une campagne → réception →
validation → entretien → verdict) + réglages · **Statut** : ÉTUDE — POINT D'ARRÊT, aucun code
modifié, aucun comportement métier touché.

**Nature de cette passe** : audit **par les normes**, indépendant des verbatims. Les verbatims
viendront **confirmer, pondérer ou compléter** — la priorisation du §10 est donc *provisoire*.
Une seule donnée d'usage est intégrée dès maintenant, pondérée comme **défaut n°1** : *la
création de campagne n'est pas comprise sans explication*. Le §4 lui est entièrement consacré.

## 0. Méthode et conditions de mesure

### 0.1 Grilles appliquées

| # | Grille | Référence |
|---|---|---|
| 1 | 10 heuristiques d'utilisabilité | Nielsen & Molich, 1990 / NN-g 1994 |
| 2 | Hiérarchie visuelle, densité, proximité | Principes Gestalt ; divulgation progressive (Nielsen) ; empan mnésique 7±2 (Miller 1956) |
| 3 | Interaction & accessibilité | Loi de Hick–Hyman ; loi de Fitts ; WCAG 2.1/2.2 niveau AA (1.4.3, 1.4.11, 2.4.7, 2.5.8, 3.3.2, 4.1.2) |

Chaque constat cite la norme qu'il applique. Aucun constat de goût.

### 0.2 Comment les mesures ont été prises

Les écrans ont été **rendus réellement**, pas lus dans le code : serveur `next dev` local
(base **dev** `sacopwwazjbibfazfmmv`, 19 campagnes / 59 candidatures actives), Chromium piloté,
session ouverte par lien magique sur le compte admin — **aucune écriture** n'a été faite
(aucune campagne créée, aucune décision posée).

- Captures : `docs/ux/captures/` (29 fichiers, 1440×900 sauf mention, + 1280×800 et 1024×768).
- Les mesures de contraste, de taille de cible, de densité et de niveaux typographiques sont
  calculées sur le **DOM rendu** (`getComputedStyle` + `getBoundingClientRect`), pas estimées.
- La matrice de contraste des jetons de couleur est calculée **sur les valeurs des jetons**
  (formule WCAG de luminance relative) : elle ne dépend pas de la machine de rendu.

### 0.3 Deux artefacts d'environnement, écartés des constats

1. **Émojis** : le conteneur de rendu n'a pas de police emoji ; ils apparaissent en tofu ou en
   Times New Roman sur les captures. Ce n'est **pas** un défaut de l'application. Le fait
   structurel retenu (§8.4) est ailleurs : ORQA utilise **161 émojis littéraux dans 57
   fichiers** *en plus* de `lucide-react` (65 fichiers) — deux systèmes d'icônes.
2. **Champs `<input type="date">`** (Reporting) : le format affiché (`mm/dd/yyyy` sur la
   capture) suit la locale du **navigateur**, pas `lang="fr"` de l'application. À vérifier sur
   un poste réel avant d'en faire un défaut.

### 0.4 Ce que l'audit ne fait pas

Aucune règle métier n'est remise en cause : les trois zones de décision, la file HITL, la
machine d'états du cycle de vie, la frontière du module de réservation, les invariants RGPD
restent **exactement** ce qu'ils sont. L'UX **explique et organise** ce qui existe.

### 1.1 Pourquoi la création a dû être expliquée des dizaines de fois

Les constats **A + B + C** se composent en un scénario qui **échoue silencieusement** :

1. L'utilisateur saisit le poste → écran 2. Le sous-titre de l'en-tête dit toujours
   « Saisissez d'abord le poste » (`CampaignCreateSheet.tsx:806`) : **l'instruction est restée
   à l'étape précédente**.
2. La section « Fiche de poste » est dépliée d'office et occupe **toute la hauteur** : les
   6 autres sections sont hors écran. Rien n'annonce qu'il y en a 7. (capture `07-create-step2.png`)
3. Il remplit ce qu'il voit, clique « **Enregistrer** » — mot qui promet une persistance qui
   n'existe pas — puis « **Créer la campagne** », bouton **primaire et actif**.
4. La campagne est créée en **brouillon** (`status: isComplete ? 'in_progress' : 'draft'`), et
   c'est **seulement là** qu'apparaît : *« Pour activer cette campagne, il reste à traiter :
   **la fiche de poste** et **les sources de réception** »*.
5. « Les sources de réception » **n'existe nulle part dans le formulaire** : la section
   s'appelle « **Flux de réception** ». Le bouton primaire devient « **Compléter la
   campagne** » et renvoie au formulaire — sans surligner quoi que ce soit.

L'utilisateur a donc rempli un formulaire sans contrainte visible, validé deux fois, et obtient
un objet inutilisable dont le motif est exprimé dans un vocabulaire qu'il n'a jamais lu.
**Chaque explication orale comble exactement ce trou-là.**

Références : `created-step-parts.tsx` (`ActivationGateNotice`), `phase-labels.ts:9-15`
(`intake: 'les sources de réception'`), `lifecycle.ts:191-200` (`canActivate`).

### 3.3 Regroupement par proximité (Gestalt) et séparation

- **Les bordures de cartes sont quasi invisibles** : `--dash-border` (#ede8e3) sur
  `--dash-surface` (#ffffff) = **1,22:1** ; `--dash-border-strong` (#d4cdc5) = **1,57:1**.
  WCAG 1.4.11 (contraste des éléments non textuels) demande **3:1**. Conséquence directe : les
  sections *sont* séparées dans le code mais ne *se voient pas séparées* — ce qui produit
  exactement l'impression de « tout sur une page » (création, fiche candidature).
- **Écrans « tout sur une page »** : création — étape 2 (la section 1 dépliée pousse les 6
  autres hors écran) ; fiche candidature (identité + score + zone + étape + pièces + profil +
  commentaire + compte rendu + 5 actions dans 460 px de large).
- **Divulgation progressive** : **déjà bien faite** dans les Paramètres (16 sections en 4
  groupes, **toutes repliées**, chacune avec un résumé d'état — capture `09-settings.png`) et
  dans l'édition de campagne (9 sections repliées, capture `16-edit-campagne.png`). **C'est le
  modèle à reprendre** ; il manque exactement là où il faudrait, à la création.

### 3.4 Occlusion

Le toast métier est en `position:absolute; bottom-6 right-6` **par-dessus** le contenu, sans
reflux et sans disparition automatique (`BusinessToast.tsx:52`). Mesuré sur les captures : il
masque la colonne de droite de la carte campagne (`04-tab-campagnes.png`), le statut de 4 lignes
de candidatures (`04-tab-candidatures.png`) et **tout le bloc « Action »** de la fiche candidature
(`10-candidature-panel.png`). Il ne s'affiche qu'une fois par session — mais cette fois-là est
la **première** de l'utilisateur.

| **Corrects mais muets** (constatent, n'orientent pas) | 14 | « Aucun entretien programmé. » · « Aucun rendez-vous sur cette période. » · « Aucune décision envoyée pour le moment. » · « Aucune campagne pour l'instant. » · « Aucune candidature en attente de validation. » |
| **Trompeurs** | 3 | « Aucune candidature en attente de validation. » alors que le badge dit 2 (§1-D) · « Aucun canal exploitable. » (rapports) · « Aucun recruteur référencé — seed admin à exécuter (runbook…) » — **message technique montré à l'utilisateur final** (`RecruitersManager.tsx:133`) |

Le patron existe donc déjà dans le produit, appliqué dans 5 cas sur 22.

### 7.2 Règle proposée : trois phrases

Tout état vide dit **(1)** ce qu'il n'y a pas, **(2)** ce qui y apparaîtra et d'où ça viendra,
**(3)** l'action qui amorce — ou, s'il n'y a rien à faire, pourquoi c'est normal.

| Écran | Aujourd'hui | Proposé |
|---|---|---|
| Validation suspendue / À examiner | « Aucune candidature en attente de validation. » | « Aucun dossier à examiner. **2 propositions de refus vous attendent** → [Voir] » *(et, si vraiment 0 : « Les candidatures dont le score tombe entre vos deux seuils apparaîtront ici. »)* |
| Entretiens / Programmés | « Aucun entretien programmé. » | « Aucun entretien programmé. Les rendez-vous apparaissent ici **dès qu'un candidat invité réserve un créneau**. » |
| Campagnes (0 campagne) | « Aucune campagne pour l'instant. » + bouton | « Aucune campagne. **Créez-en une pour commencer à recevoir des candidatures** — comptez 5 minutes. » + bouton |
| Historique des validations | « Aucune décision envoyée pour le moment. » | « Aucune décision envoyée. **Les mails partis après votre validation s'archivent ici.** » |
| Recruteurs (vide) | « seed admin à exécuter (runbook…) » | « Aucun recruteur enregistré. **Contactez votre administrateur** » + détail technique réservé au rôle admin |

### 7.3 Premières fois

Il n'existe **aucun parcours de première connexion**. Un compte neuf arrive sur un lobby dont
4 cartes sur 5 sont désactivées, puis sur un portail RH, puis sur le Bureau — une scène
décorative — avec 8 onglets tous vides.

Proposition, sans visite guidée : **le Bureau devient la vue d'ensemble et, tant qu'il n'y a
aucune campagne, il affiche un seul bloc** — « Bienvenue. Une campagne, c'est un poste à
pourvoir : sa fiche, sa grille d'évaluation, et par où les CV arrivent. → *Créer ma première
campagne* ». Les 4 étapes suivantes sont celles du §5.3. Une fois la première campagne créée,
le bloc disparaît définitivement.

### 7.4 Retours d'action — chaque action dit sa conséquence

| Action | Retour actuel | Manque |
|---|---|---|
| « Enregistrer » une section (création) | badge « ✓ Enregistré » | **Faux retour** — rien n'est enregistré (§1-B) |
| « Créer la campagne » | écran de succès | ✓ correct |
| Activer une campagne | fermeture de la feuille (ou non) | Ne dit pas **ce qui vient de démarrer** : « Le flux email est ouvert, les CV reçus seront analysés sous 30 s. » |
| Refus groupé | flash 6 s : « N candidatures refusées » | ✓ correct, avec distinction envoi/non-envoi |
| Décision HITL unitaire | flash 3,5 s | ✓ correct |
| Pointer un entretien | rafraîchissement de la liste | Aucun message ; la ligne disparaît sans dire où elle est allée |
| Poser un verdict | idem | idem — le dossier quitte l'écran sans confirmation |
| Changer un seuil | « Seuils enregistrés… Appliqués aux prochaines candidatures. » | ✓ **exemplaire** — dit l'effet *et* la portée |
| Échec d'association de boîte mail | avertissement sur l'écran de succès | ✓ correct |

Modèle à généraliser : la phrase des seuils (`DecisionThresholdsBlock.tsx:69-70`) — *quoi a
changé* + *à partir de quand* + *sur quoi ça ne s'applique pas*.

### 8.1 État des lieux

| Dispositif | Nombre | Limite |
|---|---|---|
| `title=""` (infobulle native) | **95** | Souris uniquement, ~1 s de latence, non stylable, invisible au clavier et au tactile |

| Bouton « ? » / pastille d'aide | **0** | — |
| Texte d'aide **associé** au champ (`aria-describedby`) | **0** | Les textes d'aide existants sont visuellement proches mais jamais reliés |

### 8.2 Où l'aide manque et évite une question (par ordre de fréquence de la question)

| Endroit | Question que l'utilisateur pose | Phrase à poser sous le champ |

| Création § arrivée des candidatures | « Pourquoi je ne reçois rien ? » | « Sans canal d'arrivée, aucune candidature ne parviendra à cette campagne. » |

| Création/édition § décision automatique | « Il se passe quoi sous 10 ? » | *(déjà écrit en édition, à reprendre tel quel en création)* |
| Création § recruteur référent | « À quoi ça sert ? » | « C'est son agenda qui est proposé aux candidats invités. » |
| Création § réservation d'entretien | « Native ou lien d'agenda ? » | « **ORQA** propose les créneaux du référent. **Lien d'agenda** envoie vers l'outil configuré dans les Paramètres. » |
| Création § diffusion | « Ça publie vraiment ? » | « Seules l'annonce générique et l'APEC publient aujourd'hui ; les autres canaux servent de mémo. » |
| Boîte mail associée | « Comment le CV est rattaché ? » | « Les CV reçus sur cette boîte sont rattachés si l'objet porte **CAMP-2026-419**. » |
| Paramètres § agendas | « Pourquoi 0 créneau ? » | *(déjà fait : « vérifie les plages, le… ») ✓* |
| Ruban Candidatures | « C'est quoi “À valider” ? » | Légende repliable : une ligne par étape |
| Fiche candidature | « Pourquoi ce score ? » | Le bouton « Rapport d'analyse » existe — à **nommer** « Voir le détail du score » |

### 8.3 Règles

1. L'aide qui évite une erreur est **permanente et sous le champ**, pas dans une infobulle.
2. L'aide qui explique un terme est **au survol *et* au clavier**, via un composant maison
   (`ⓘ` focusable + `aria-describedby`), jamais `title`.
3. Aucune visite guidée. Un seul bloc de bienvenue, qui disparaît après la première campagne.

### 10.3 Hiérarchie proposée

**Quotidien — barre principale (4 entrées) :**
`Aujourd'hui` (ex-Bureau, refondu en liste de ce qui attend) · `Candidatures` ·

nommer deux onglets voisins).

**Occasionnel — second rang :** `Campagnes` · `Sourcing` · `Vivier` · `Reporting`.

**Réglages :** engrenage → Paramètres (inchangé, c'est le meilleur écran du produit).

Effet mesurable : 8 entrées de premier niveau → **4**, la zone « onglets » repasse sous le
seuil de 7 (§3.1).

### 10.4 Réduction des chemins multiples

| Action | Chemins actuels | Proposé |
|---|---|---|
| Poser un verdict | (1) Entretiens → « En attente de verdict » → Décider · (2) Fiche candidature → bloc Action · *(retiré du dashboard résiduel)* | **Garder les 2** — ce sont deux contextes légitimes (file de travail / dossier) ; **unifier le bloc** (déjà fait : `InterviewDecisionBlock` partagé) et **le libellé** (« Retenu » partout, pas « GO définitif ») |

| Validations vivier | onglet **+** route `/validations-vivier` | idem |
| Reporting | onglet **+** route `/reporting` | idem |

### 10.5 Deux corrections de navigation immédiates

1. **Destination après connexion** : `/rh/recrutement` plutôt que `/app`
   (`next-path.ts:11`). Le lobby reste accessible par le fil d'Ariane. Économie : **2 clics à
   chaque session**, pour 100 % des utilisateurs.
2. **Le chat ne doit plus recouvrir la barre d'onglets** : ouvert, il rend 3 onglets sur 8
   inatteignables (§2.2). Soit il pousse le contenu, soit il s'arrête sous la barre.
